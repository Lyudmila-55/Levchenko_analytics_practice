= Документация к системе управления проектами

== Задание
[%collapsible]
====
**Контекст:**
Вы работаете в компании, занимающейся разработкой платформы для онлайн- управления проектами и командной работы. Ваша задача заключается в создании подсистемы для менеджеров проектов и членов команд, которая позволит им более эффективно взаимодействовать, планировать задачи и отслеживать прогресс.
Основные функции системы включают:
● Регистрация и создание профилей пользователей
● Заполнение данных по проектам.
● Инструменты для создания и назначения задач, которые включают возможность
устанавливать приоритеты, сроки и назначать ответственных.
● Календарь для планирования встреч и сроков выполнения задач.
● Функционал для хранения документов и файлов
● Инструменты для общения и обсуждения, включая возможность создания чатов, обсуждений и видеозвонков прямо внутри платформы.

**Ваша задача** — проработать документацию для данной системы
Детали процесса и конкретное назначение системы необходимо придумать
самостоятельно.

**Задание:**
**Документирование:**
● Создайте документацию по требованиям в формате Docs as Code.
Структурируйте её так, чтобы она легко редактировалась и обновлялась.
Используйте AsciiDoc или Markdown.
● Разработайте структуру документации. В документации обязательно должно
быть
    ○ описание бизнес-процессов
    ○ описание заинтересованных сторон,
    ○ функциональные и нефункциональные требования
    ○ структура БД
    ○ архитектура системы
    ○ описание взаимодействия компонентов системы

**Анализ требований:**
● Изучите процессы компании. Определите ключевых заинтересованных стороны.
● Зафиксируйте полученные данные и составьте список функциональных и
нефункциональных требований. Убедитесь, что требования соответствуют
принципам, изложенным в BABOK.
Требование: Должно быть описано не менее 20 требований к системе

**Моделирование БП:**
● Создайте диаграмму БП в нотации BPMN (Business Process Model and Notation)
в Camunda
Требование: Диаграмма должна содержать не менее 10 задач и 5 событий.
Задачи организованы в пулы и дорожки

**Моделирование базы данных:**
● Для моделирования используйте PlantUML Information Engineering Diagram
● Создайте логическуй модель данных системы
● Определите сущности, которые будут использоваться в системе
● Определите атрибуты каждой сущности.
● Установите отношения между сущностями.
Требование: ER диаграмма должна содержать не менее 5 сущностей

**Описание верхнеуровневой архитектуры системы**
● Создайте верхнеуровневую архитектуру системы с использованием диаграммы
C4 в PlantUML. Эта диаграмма должна отображать основные компоненты
системы и их взаимодействие.
● Разработайте диаграмму контекста и диаграмму контейнеров
Требование: Микросервисная архитектура

**Описание взаимодействия компонентов системы:**
● Создайте диаграмму последовательности взаимодействия компонентов
системы, используя PlantUML. Эта диаграмма должна показывать, как
различные компоненты взаимодействуют друг с другом. Учтите взаимодействия
между клиентом, системой, базой данных и внешними сервисами.
● Обозначьте основные сообщения и ответы на различных этапах процесса
Требование: Не менее двух диаграмм последовательности. Не менее 3
объектов в каждой
====

== Введение
Документация описывает подсистему для менеджеров проектов и членов команд, которая позволит им
более эффективно взаимодействовать, планировать задачи и отслеживать прогресс.

== Цель
Создание единого пространства для коммуникации и управления задачами между менеджерами проектов и членами команды, способствующего прозрачности и эффективности работы.

= Описание бизнес-процессов
== 1.1 Основные бизнес-процессы компании

=== 1. Инициация нового проекта
*Триггер*: Поступление заявки от клиента или внутренняя инициатива  
*Участники*: Менеджер продаж, Руководитель компании, Менеджер проекта  
*Входные данные*:  
- Устный/письменный запрос клиента  
- Рыночные исследования (для внутренних проектов)  

*Основные этапы*:  
1. Первичный анализ требований клиента  
2. Оценка осуществимости (feasibility study)  
3. Расчет предварительной сметы  
4. Согласование условий с клиентом  
5. Подписание договора/утверждение приказа  

*Результат*:  
- Утвержденное техническое задание  
- Подписанный договор  
- Назначенный менеджер проекта  

=== 2. Планирование проекта
*Триггер*: Получение утвержденного ТЗ  
*Участники*: Менеджер проекта, Команда, Эксперты  
*Входные данные*:  
- Техническое задание  
- Доступные ресурсы  

*Основные этапы*:  
1. Декомпозиция работ (WBS)  
2. Оценка трудозатрат  
3. Построение сетевого графика  
4. Распределение ресурсов  
5. Определение контрольных точек  

*Результат*:  
- Календарный план проекта  
- Бюджет проекта  
- Матрица ответственности  

=== 3. Реализация проекта
*Триггер*: Утверждение плана проекта  
*Участники*: Исполнители, Менеджер проекта, Контролирующие органы  
*Входные данные*:  
- Утвержденный план  
- Выделенные ресурсы  

*Основные этапы*:  
1. Запуск выполнения работ  
2. Мониторинг прогресса  
3. Управление изменениями  
4. Решение возникающих проблем  
5. Регулярная отчетность  

*Результат*:  
- Выполненные работы  
- Промежуточные отчеты  
- Акты выполненных работ  

=== 4. Контроль качества
*Триггер*: Завершение ключевых этапов  
*Участники*: QA-отдел, Менеджер проекта, Технические специалисты  
*Входные данные*:  
- Результаты работ  
- Стандарты качества  

*Основные этапы*:  
1. Проведение тестирования  
2. Анализ соответствия требованиям  
3. Фиксация дефектов  
4. Устранение недостатков  
5. Подписание актов приемки  

*Результат*:  
- Отчет о качестве  
- Сертификаты соответствия  
- Доработанные продукты  

=== 5. Завершение проекта
*Триггер*: Выполнение всех работ  
*Участники*: Руководство, Команда, Клиент  
*Входные данные*:  
- Итоговые результаты  
- Документация проекта  

*Основные этапы*:  
1. Финальная приемка  
2. Финансовый расчет  
3. Анализ эффективности  
4. Архивация документов  
5. Роспуск команды  

*Результат*:  
- Закрытый проект  
- Отчет о выполнении  
- Извлеченные уроки

== 2. Заинтересованные стороны
|===
| Роль             | Интересы
| Менеджер проекта | Создание, планирование, назначение задач
| Член команды     | Получение задач, коммуникация, отчётность
| Администратор    | Поддержание инфраструктуры и безопасности
| Владелец/Клиент  | Контроль прогресса, отчёты, доступ к данным

== 3. Требования
=== 3.1 Функциональные требования
FR1:: Система должна предоставлять возможность регистрации новых пользователей через форму ввода email и пароля без обязательного подтверждения по email.
FR2:: Система должна предоставлять пользователю возможность редактирования данных своего профиля (имя, аватар, описание, роль) в любой момент времени.
FR3:: Система должна позволять пользователю с ролью «менеджер проекта» создавать новый проект, указывая его название, описание и цели.
FR4:: Система должна предоставлять возможность менеджеру проекта добавлять участников в проект с назначением ролей (участник, наблюдатель, администратор).
FR5:: Система должна позволять менеджеру проекта указывать дату начала и окончания проекта при его создании или редактировании.
FR6:: Система должна предоставлять возможность создания задач с обязательными полями: заголовок, описание, приоритет, срок выполнения.
FR7:: Система должна позволять назначать одного или нескольких пользователей ответственными за выполнение задачи.
FR8:: Система должна отображать текущий статус задачи (например: «новая», «в работе», «на проверке», «завершена») и позволять его изменять в процессе работы.
FR9:: Система должна отображать задачи в виде календарного представления, синхронизированного с установленными сроками выполнения задач.
FR10:: Система должна предоставлять возможность создания календарных событий (встреч, звонков, планёрок) с указанием даты, времени и участников.
FR11:: Система должна предоставлять возможность загружать, просматривать и скачивать файлы, прикреплённые к задачам и проектам.
FR12:: Система должна поддерживать версионность документов, включая автоматическую нумерацию версий и возможность отката к предыдущей версии.
FR13:: Система должна предоставлять встроенный чат внутри каждого проекта, доступный для всех участников проекта.
FR14:: Система должна поддерживать видеозвонки между двумя и более участниками проекта через встроенный веб-интерфейс.
FR15:: Система должна позволять пользователям создавать обсуждения по задачам в виде вложенных комментариев.

=== 3.2 Нефункциональные требования
NFR1:: Система должна обеспечивать среднее время отклика пользовательского интерфейса не более 2 секунд при стандартной нагрузке.
NFR2:: Система должна обеспечивать стабильную работу при одновременной активности не менее 1000 пользователей.
NFR3:: Все данные, передаваемые между клиентом и сервером, должны быть защищены протоколом HTTPS с TLS 1.2 и выше.
NFR4:: Система должна предоставлять опцию двухфакторной аутентификации для всех зарегистрированных пользователей.
NFR5:: Система должна обеспечивать доступность не менее 99.9% в течение календарного месяца (включая плановые обновления).
NFR6:: Система должна автоматически создавать резервные копии всех пользовательских данных не реже одного раза в сутки.
NFR7:: Система должна быть способна масштабироваться горизонтально, добавляя новые экземпляры сервисов при росте нагрузки.
NFR8:: Хранилище файлов должно автоматически масштабироваться при превышении 80% текущего объёма без потери данных.
NFR9:: Пользовательский интерфейс должен быть адаптирован для корректной работы на мобильных устройствах (минимум: Android, iOS).
NFR10:: Система должна поддерживать локализацию интерфейса минимум на три языка: русский, английский, испанский.

== 4. Структура базы данных
=== 4.1. Структура сущностей базы данных
==== User
|===
| Атрибут       | Тип данных | Примечание
| id            | UUID       | Идентификатор пользователя (PK)
| name          | String     | Имя пользователя
| email         | String     | Уникальный email
| role          | String     | Роль (manager, member, admin)
| is_active     | Boolean    | Активен ли аккаунт
| last_login_at | DateTime   | Дата последнего входа
| created_at    | DateTime   | Дата создания записи
| updated_at    | DateTime   | Дата последнего изменения
|===

==== Project
|===
| Атрибут     | Тип данных | Примечание
| id          | UUID       | Идентификатор проекта (PK)
| title       | String     | Название проекта
| description | Text       | Описание проекта
| owner_id    | UUID       | Внешний ключ (FK → User.id)
| status      | String     | Статус проекта
| start_date  | Date       | Планируемое начало
| end_date    | Date       | Планируемое окончание
| created_at  | DateTime   | Дата создания проекта
| updated_at  | DateTime   | Дата обновления проекта
|===

==== Task
|===
| Атрибут        | Тип данных | Примечание
| id             | UUID       | Идентификатор задачи (PK)
| title          | String     | Название задачи
| description    | Text       | Описание задачи
| status         | String     | Статус (new, in_progress, done)
| priority       | String     | Приоритет (low, medium, high)
| due_date       | Date       | Крайний срок
| start_date     | Date       | Дата начала
| assignee_id    | UUID       | Внешний ключ (FK → User.id)
| creator_id     | UUID       | Внешний ключ (FK → User.id)
| project_id     | UUID       | Внешний ключ (FK → Project.id)
| estimated_time | Float      | Оценка времени (часы)
| spent_time     | Float      | Затраченное время
| created_at     | DateTime   | Дата создания
| updated_at     | DateTime   | Дата обновления
|===

==== File
|===
| Атрибут     | Тип данных | Примечание
| id          | UUID       | Идентификатор файла (PK)
| name        | String     | Имя файла
| url         | String     | Путь к файлу
| size        | Integer    | Размер в байтах
| uploaded_by | UUID       | Внешний ключ (FK → User.id)
| project_id  | UUID       | Внешний ключ (FK → Project.id)
| task_id     | UUID       | Внешний ключ (FK → Task.id)
| created_at  | DateTime   | Дата загрузки
|===

==== Message
|===
| Атрибут    | Тип данных | Примечание
| id         | UUID       | Идентификатор сообщения (PK)
| sender_id  | UUID       | Внешний ключ (FK → User.id)
| content    | Text       | Содержимое сообщения
| timestamp  | DateTime   | Дата и время отправки
| project_id | UUID       | Внешний ключ (FK → Project.id)
|===

==== CalendarEvent
|===
| Атрибут    | Тип данных | Примечание
| id         | UUID       | Идентификатор события (PK)
| title      | String     | Название события
| description| Text       | Описание
| start_time | DateTime   | Время начала
| end_time   | DateTime   | Время окончания
| created_at | DateTime   | Дата создания
| project_id | UUID       | Внешний ключ (FK → Project.id)
| creator_id | UUID       | Внешний ключ (FK → User.id)
|===
